# Local bootstrap upgrade

Read only for agm-release bootstrap upgrade or legacy upgrade. Read the target instructions and prove its profile; never bootstrap the skill-package root. These actions need Node and the bundle, not product release tooling.

## Preserving and replacement modes

`agm-release bootstrap upgrade` upgrades local bootstrap files while preserving valid project customizations. Resolve the actual target and supported kind, inspect installed rules and run `project-bootstrap.mjs plan --target <project> --kind <kind>` without --upgrade. Apply compatible missing/recognized-template updates through `project-bootstrap.mjs apply` with the same target/kind; its backups and receipt tracking remain mandatory. For custom content, inspect the scoped delta, back up the affected files, merge maintained rules while retaining project-specific instructions, and reconcile the helper's normal plan/receipt only after verifying the merged contract. Do not merely replace the version marker. Ask only about an unresolved conflicting project rule; the command already authorizes this maintenance. README changes stay inside the managed Deployment block. Finish after diff, hashes/merged-rule evidence and freshness verification, without .NET/CLI readiness or release steps. Never convert this action silently into legacy replacement mode.

`agm-release upgrade` is the legacy explicit replacement action alongside the nine release actions. Prefer `agm-release bootstrap upgrade` for an upgrade that preserves custom project rules. The explicit request authorizes replacing bundled contract files even when customized: AGENTS.md, CLAUDE.md, GEMINI.md, CURSOR.md, release-notes/README.md, and only the marked Deployment block in root README.md. Read and show the scoped replacement diff, back up every overwritten file, apply the active bundle, verify hashes/version/receipt and report updated paths. No extra replacement approval is needed for this explicit action. Never overwrite the whole project README, Jenkinsfiles, application/package versions, changelog, project memory or historical versioned notes. Ambiguous/malformed README block boundaries require scoped resolution, not guessing. No commit/push/tag/deploy unless separately requested.

For a manually reviewed custom merge, save exact original bytes first at `.agrimap-agent/runtime/bootstrap-backups/<original-sha256>/<target-relative-path>`, then edit only the scoped contract. Inspect the full resulting rules against the active bundle and project requirements. Supply a temporary JSON array to normal `plan` and `apply` via `--reviewed-merges <json-file>`; each entry contains `target`, `sha256` (merged bytes), `backupHash` (original bytes) and `reason` (the actual review decision). Only bundled targets are accepted. The helper verifies fingerprints, backups, AGENTS version marker and README boundaries; it records the merge with this exact bundle hash. Subsequent edits or bundle changes invalidate the recorded approval. This proves byte-level review provenance, not semantic correctness: never use it to waive missing canonical rules or simply stamp a marker. Normal plan must report current after apply; report custom merged paths separately from byte-exact templates. Do not combine reviewed-merges with legacy --upgrade replacement mode.

For legacy replacement only, use `project-bootstrap.mjs plan --upgrade --target <project> --kind <kind>`, then `project-bootstrap.mjs upgrade --target <project> --kind <kind>`. Both local actions need Node and the proven target/profile, not .NET/release CLI installation or branch promotion. They do not change the nine release sequences: all nine still check installed contract freshness under release-and-bootstrap.md; ordinary release requests do not implicitly authorize overwriting customized contracts via upgrade mode.
