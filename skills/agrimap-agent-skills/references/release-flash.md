# Delta-only release (--flash)

Agent-chat modifier, not an executable or .NET CLI option. Accept it on `release full|inhouse|production`, `prepare inhouse|production` and `pipeline inhouse|production`; normalize `full --flash`, `inhouse --flash`, `production --flash` to the `release` commands. The bare flag may precede or follow the command words. Reject valued/duplicate flags, unknown options and --flash on indexing/promote/bootstrap before writes. Without --flash, existing command semantics are unchanged. Quoted examples authorize nothing.

## Scope override

Flash uses the same command expansion and owner/publication boundaries in release-steps.md, replacing I with delta review below. With prepare/pipeline, flash narrows the stale-index prerequisite and V/D review to that delta; pipeline still never creates a missing candidate. H/P reconcile only delta changelog/notes and minimal checkpoints; they do not reintroduce full indexing through a stale/missing project.md prerequisite. This explicit mode replaces this package's full Backfill, historical catalog and README capability inventory obligations for this invocation. It does not mark project-wide indexing complete, silently rewrite target instructions or override higher-priority restrictions. Resolve a genuinely incompatible mandatory target gate concisely; never silently fall back to full indexing.

## Fast path

1. Read applicable instructions and existing release checkpoints once. Inspect Git status including staged/unstaged/untracked/deleted paths, remote and selected owner pairs. Fetch the required refs together; inspect all three release branch pairs and safely fast-forward behind-only locals in the same directory. No clone/worktree, stash/reset, unrelated publication or automatic feature integration.
2. Select an evidence-backed baseline per selected environment: explicit owner baseline, verified previous release checkpoint/tag matching that owner, or verified remote deployment-branch SHA. Confirm ancestry and actual owner values; do not choose the largest tag, invent a baseline or reuse a Production tag as Inhouse history without proof. If missing/ambiguous, finish independent checks and ask one baseline question; do not scan all history. Review baseline-to-candidate committed changes plus all dirty paths, reading changed content and affected dependencies only. Record exclusions, secrets/ownership blockers and limits.
3. Prepare or resume the selected versions once (explicit target, otherwise owner PATCH+1). Full prepares both before publication; Production-only leaves Inhouse unchanged; Inhouse creates no Production notes/index/tag. Update changelog for this delta, and Production release.md/notes when selected. Keep existing historical text. No README/catalog reconstruction. Create only the minimal factual project checkpoint if required, labelled delta-only with baseline, candidate, covered paths, verification and remaining actions.
4. Verify scoped owner pair/version and allowed diffs, secret risks, notes provenance/completeness, git diff --check, ancestry and tag collisions. Reuse test/build evidence only while content, dependencies, configuration and tools match; verify the rest proportionally. Flash is not skip-tests. SHA identifies content, not correctness. Use Git commit/tree/blob identities for tracked content; hash untracked/release artifacts only as needed, not every file repeatedly.
5. Follow D/J/Q/C/T for the selected command, with one frozen candidate and exact-path staging. Reuse completed remote checkpoints. Refresh remote state before publication and after human approval to detect races, not before each read command. Inhouse stops at jenkins; Production/full use one concise Production branch/tag confirmation (or matching existing approval), then verified jenkins-release and annotated tag publication. Never forward --flash to the .NET CLI, force-push, move tags or edit CI triggers.
6. Finish with one concise checkpoint/result: command, baseline/candidate, owner versions, branch/tag results, verification reused/run, excluded work, delta-only coverage and the mandatory release-timing.md output block (Elapsed, Active, Waiting, per-step durations; explicit UNKNOWN/reason if missing). Respect target-required recording without creating optional duplicate reports. Fold eligible history into the D candidate; later history is carried forward per release-timing.md. Never amend it into the candidate or start another release loop.

## Avoid repeated overhead

Reuse tool/source compatibility evidence within the run while binary/runtime identity is unchanged. Prefer supported read-only gates; use release-tools.md for actual missing/incompatible tools, not repeated installation or live prepare probes. A missing tool is not permission to waive a mandatory gate. Reuse successful bootstrap freshness evidence until bundle/target content changes. Batch independent read-only checks where practical, but serialize Git mutations and check every exit code. On uncertain push outcome, inspect remote refs before retrying; tag failure resumes only the tag checkpoint.

No guaranteed duration or green-deployment claim. Single push per ref applies (release-steps.md); Flash does not alter server triggers.
